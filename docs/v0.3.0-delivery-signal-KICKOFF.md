Orientation for a FRESH session implementing the **delivery-signal enhancement**
in prompt-it. There is no separate spec doc — **this note IS the spec**: the
design was settled in the `how-to-next-prompt` session (Engine-Core, 2026-07-28)
and is reproduced in full below.

Read this first. For anything it leaves out:
`/read-chat "how-to-next-prompt"`.

## What you're building (one line)

Make prompt-it decide, from signals in the session, whether its compiled prompt
should be **run in the current session** or **pasted into a fresh one** — and
say which, in one line of its output.

## Why (the problem this fixes)

prompt-it Mode 1 is named the "new-session compiler" and its emit contract
assumes a fresh session (`SKILL.md:130` — *"Setup lines only if genuinely
needed (≤2, e.g. 'run from the Engine-Core repo root')"*; the root README copy
says the block is *"ready to paste into a fresh session"*). That assumption is
wrong for a common case, and wrong in a way nothing recovers from:

**A compiled prompt is text. Anything in the session that is not text does not
travel.** Screenshots are the sharp case — and `/read-chat`, the standard
escape-hatch prompt-it leans on, *explicitly strips attachments* from its
digest ("The digest already strips tool-result/attachment/snapshot noise"). So
across a session boundary, pasted images are not degraded, they are
**unrecoverable**.

Real case that motivated this (2026-07-28): session `praxya-feedbacks-pt5`
compiled a Moretti feedback cycle with `/prompt-it`, carrying **six
screenshots** as the primary evidence (Radar 502, stale queue, clean queue, the
disabled GA4 field, empty Pulse cards, OpenRouter balance). The user ran the
compiled prompt **in the same session** — correctly, because a fresh session
would have lost every screenshot. prompt-it's own setup line had advised a
fresh session. The advice was wrong and the user overrode it manually.

## First concrete slice (do this first)

Edit the **shared SKILL.md body** — Hard Rule 1's shape line, the emit-contract
setup-line slot, the output-hygiene restatement, and add the new
dangling-evidence guard. Nothing else. Then stop.

**Anti-pattern — do NOT introduce a user-facing mode flag** (`--same-session`,
a "which session?" question, a mode selector). The whole point is that prompt-it
infers this from signals it can already see. A question here would violate the
skill's own Rule 2 (emit-first; appended questions must be *earned* by a failed
lookup and must offer ≥2 concrete candidates). It would also be exactly the
bureaucracy the user rejected when scoping this work.

## The design (locked decisions)

1. **It is a signal-driven decision prompt-it makes itself, not a user-facing
   mode.** *Why:* a mode toggle is bureaucracy and would violate the skill's
   earned-questions rule; the signal is detectable from the conversation.

2. **The signal table:**

   | Signal present in the session | Delivery |
   |---|---|
   | Load-bearing images, pasted screenshots, uploaded files | **run here** — text cannot carry them |
   | Live session state the run needs (open CDP browser, running dev server, active worktree) | **run here** |
   | Pure text ask; every pointer is a file path | **fresh session** — clean context wins |
   | No signal either way | fresh for overnight/autonomous runs; here for attended work |

   *Why the tiebreak:* context hygiene matters most on long unattended runs;
   for attended work the cost of a second session (and its ledger card) exceeds
   the benefit.

3. **The output change is ONE line, replacing the existing setup-line slot** —
   not a new section. Shape stays `fence → 🎯 → 💡 → delivery line → (≤3 optional
   questions)`. *Why:* Rule 1 fixes the response shape; adding a section would
   break the skill's own output contract and likely regress the eval.

   ```
   ▶ Run here — this session holds 6 screenshots the prompt can't carry.
   ▶ Paste into a fresh session. Run from /Users/macbook/Workspace/Engine/Engine-Core.
   ```

4. **New guard — the dangling-evidence rule.** When delivery is *fresh session*,
   the emitted block must NEVER reference in-session evidence ("the 5
   screenshots above", "the error I pasted"); it must describe the evidence in
   words or point at persisted file paths. When delivery is *run here*, such
   references are allowed. *Why:* this is the same failure class as the existing
   dead-pointer rule (a pointer the target cannot resolve), and it is currently
   **unguarded** — today a fresh-session prompt can silently ship a reference to
   images the target session cannot see.

5. **The evidence extractor is OUT of scope for 0.3.0.** (Dumping session images
   from the transcript `.jsonl` to `.prompt-it/evidence/` and `@`-referencing
   them — which would work, since Read renders image files — is the v0.3.x
   stretch.) *Why:* the user explicitly scoped this release "light"; ship the
   signal line and see whether the extractor is ever missed.

6. **Version is 0.3.0, not 0.2.2.** *Why:* new behavioral rule, not a defect fix.

## How to run + test

The binding gate is the 20-sample eval suite. 0.2.1 is certified **20/20**
(`eval/runs/v0.2.1-final/`, judged against `eval/expected-prompts.md` property
checklists).

```bash
cd ~/Workspace/Devotts/prompt-it
eval/scripts/run-eval.sh S01 eval/runs/v0.3.0-phase1     # one sample
# samples live in eval/runs/.samples/S01.txt … S20.txt
```

The script pipes `/prompt-it <sample>` into a **fresh headless `claude -p`
session** and writes `<SID>.md` / `<SID>.err` to the outdir. Judgment is a
separate pass (see `judgment-A.md` … `judgment-D.md` in the 0.2.1 run folder for
the format).

⚠ `EVAL_MODEL` defaults to **sonnet** in the script, but the CHANGELOG records
the 0.2.1 20/20 baseline as run on the **Fable** tier with Fable-tier judges.
Set `EVAL_MODEL` to match the baseline or the comparison is not apples-to-apples.

## Gotchas to carry forward

- **G1 — Two SKILL.md files, one shared body.** `SKILL.md` (root) is the plugin
  file plus an Install + Security section (lines 147–177) and extra frontmatter
  (license/homepage/metadata/keywords). Lines 1–146 are **byte-identical**.
  Every body edit must land in both, identically. Verify with:
  `diff <(sed -n '/^# \/prompt-it/,$p' SKILL.md) <(sed -n '/^# \/prompt-it/,$p' plugins/prompt-it/skills/prompt-it/SKILL.md)`
  — the only expected diff is the Install/Security tail.
- **G2 — Two version fields**, and they must stay in lockstep:
  `plugins/prompt-it/.claude-plugin/plugin.json:4` and
  `.claude-plugin/marketplace.json:13`.
- **G3 — The output shape is stated TWICE** in the body (Hard Rule 1 at line 28,
  Output hygiene at line 134). Editing one and not the other leaves the skill
  contradicting itself — a defect the eval may or may not catch.
- **G4 — Root SKILL.md Install section says the block is "ready to paste into a
  fresh session"** (~line 170). That becomes conditionally wrong with this
  change; update the copy.
- **G5 — `run-eval.sh` exercises the INSTALLED plugin, not the working tree.**
  It is installed from the GitHub marketplace at
  `~/.claude-8ftools/plugins/cache/devotts/prompt-it/0.2.1/` (per
  `installed_plugins.json`, pinned to a git SHA). **Editing the repo does not
  change what the eval runs** until you reinstall/update the plugin. Running the
  eval against an unreinstalled plugin will silently re-certify 0.2.1 and tell
  you nothing.
- **G6 — Pre-existing uncommitted change**: `D docs/prompt-examples.txt` was
  already deleted-not-committed before this work. Not yours; decide separately.
